# IdeaCard 当前版本评审

评审对象：当前工作区的 `desktop/`，包括尚未提交的实现；不以早期 `prototype/` 为准。

方法：独立界面设计评审（design_review）、独立检测与浏览器证据（ui_evidence），主评审检查保存、AI、数据读取和工程验证。原生界面查看了有 23 张卡片的收集箱及 AI 抽屉；没有编辑真实卡片、删除数据或发送模型请求。代码推导的失败路径不等同于在真实数据上复现。

## 判断

当前产品的主要机会是打通“收集 → 找回 → 阅读 → 写出自己的判断”。捕获方式、概念注释、单卡 AI 延伸已有基础，下一轮应优先保障资料可靠性、提高整理和阅读效率。深绿导航与近白工作区的视觉方向可以保留。

当前范围以 PRODUCT.md 为准：多卡分析、自动标签、云同步和研究代理不作为这一轮的默认扩展方向。

## 近期优先处理

### P1：正文读取失败后仍允许编辑，存在覆盖结构化内容的风险

CardDetail 初始化使用 `originalContent` 重建纯文本正文。读取结构化正文失败后只记录错误并结束 loading；编辑器的只读条件仅检查归档和 loading。因此读取失败后用户仍能编辑这份不含图片、概念标注的降级正文。随后若保存成功，后端会按新正文替换旧文档，并清理不再引用的图片和概念引用。

这是静态代码确认的失败路径，未在真实卡片上破坏性验证。建议将读取状态明确区分为 loading、ready、error；error 保持正文只读，提供重新加载；只有成功加载的文档才能覆盖保存。增加“带图片与概念的正文加载失败 → 用户尝试编辑”的回归场景。

证据：`desktop/src/features/inbox/CardDetail.tsx:149,200,767`；`desktop/src-tauri/src/repository/document_repository.rs:128,152,179`。

### P1：AI 请求可能使用上一次保存的内容

自动保存有 1,200ms 延迟。AI 延伸与概念解释直接发送 cardId 等参数，没有先等待当前草稿保存；后端从数据库读取上下文。修改正文或“我的想法”后立即发问，尤其在已有提问草稿的情况下，可能让 AI 看到旧内容。概念解释还有独立定位问题：长文中同一词出现多次，后端使用字符串首次匹配来找周边原文，无法确认用户实际选中哪一处。

建议发送前取得一致的草稿快照，或显式等待保存完成且在失败时阻止发送；概念解释传递实际选区附近文本或可校验的选区位置。验证“编辑后立即提问”和“长文选择第二处同名概念”两个场景。

证据：`CardDetail.tsx:83,452,955`；`desktop/src-tauri/src/commands/ai_commands.rs:237,359`；`desktop/src-tauri/src/ai/service.rs:207`。

### P2：AI 生成过程应允许稳定回看，并保留部分成果

当前每次流式增量都强制滚到底部。用户向上读第一段或历史消息，会被新字符拉回底部。停止和失败时清空 pendingTurn，已经展示的部分回答随之消失；后端仅在完整生成成功后保存一轮对话。

建议仅在用户接近底部时跟随；向上滚动后显示“回到最新”。停止或失败保留部分回答，标注“已停止 / 未完成”，支持复制与重试。是否持久化未完成回复需要单独设计，不能将其当作完整回答。

证据：`desktop/src/features/ai/AiConversation.tsx:73,124,190`；`desktop/src-tauri/src/commands/ai_commands.rs:264`。

## 产品与界面改进

### P1：让阅读获得主要空间

原生界面中，卡片标题在顶部和标题输入框重复；正文默认 300px 高并内部滚动，空的“我的想法”仍占六行。打开 AI 后，虽然侧栏已折叠，列表仍占较多宽度，正文阅读继续受到限制。

建议标题原位编辑；在保留现有拖动调整正文高度的基础上，增加明确的“展开原文 / 专注阅读”；空想法输入区紧凑呈现、输入时展开；AI 打开时允许收窄或收起列表。先改 DESIGN.md，再修改实现。

证据：`CardDetail.tsx:655,733,759,782`；`desktop/src/shared/styles/global.css:1123`。

### P2：围绕整理状态和找回建立轻量工作流

已有待整理、已整理状态，但收集箱只能按来源筛选。当前搜索只在当前工作区内对标题、正文、想法、来源名称做字符串匹配，没有匹配片段或概念/AI 回答搜索。卡片多起来后，用户需要逐张扫状态，命中后也要自己寻找关键词。

建议先加“全部 / 待整理 / 已整理”、上一张/下一张键盘操作、关键词高亮和匹配片段；再提供明确的跨收集箱与归档搜索范围。概念搜索可与卡片搜索并列呈现，避免无说明地混合结果。无结果时区分关键词未命中与来源为空，提供清除筛选。

证据：`desktop/src/pages/InboxPage.tsx:101,129,146`；`desktop/src/features/inbox/CardList.tsx:35`。

### P2：AI 延伸补上“开始”和“收尾”

空态只写“还没有 AI 讨论记录”，输入框无问题示例；联网不可用时没有说明是模型能力还是设置导致。回答支持复制和重新生成，但没有直接沉淀为自己的想法的操作。

建议首次展示 2–3 个简短问题示例，如“有哪些反例”“这个想法遗漏了什么”；说明 Enter 发送、Shift+Enter 换行；禁用联网说明具体原因。回答或选中文字提供“追加到我的想法”，用户主动触发并可撤销，保留来源，避免自动覆盖原有判断。

证据：`AiConversation.tsx:225,295,312,356`；`CardDetail.tsx:911`。

### P2：降低删除权重，补齐可访问性

详情中最醒目的实心按钮是红色删除，与阅读和整理的主要任务不匹配。建议常驻入口改成低强调按钮或更多菜单，最终删除确认仍保留红色主按钮和默认取消焦点。

卡片列表选中只通过 CSS 展示，应补上语义状态并缩短读屏名称；视觉上被截断的全文现在仍进入按钮名称。独立浏览器检查还发现快速记录按 Esc 不关闭，Tab 可离开弹窗；对应实现为带 dialog 语义的普通元素，没有统一焦点约束。建议统一弹窗的 Escape、焦点循环与关闭后焦点返回；有草稿时先明确保留策略。

证据：`CardDetail.tsx:682`；`CardList.tsx:43`；`desktop/src/features/concepts/ConceptPage.tsx:46` 可作为选中语义的已有参照。

### 建议纳入下一阶段：本地备份与导出

当前本地数据库与附件已成为真实资料的存储位置，但未发现用户可用的整库备份、恢复或卡片导出入口。建议先做包含数据库和附件的一致性备份与可验证恢复，再支持单卡 Markdown + 附件导出。无需为此提前引入云同步。恢复流程涉及数据替换，实施时需要用户确认具体方案。

## 工程改进

- **拆分复杂状态的职责。** CardDetail 当前 987 行，同时处理草稿、自动保存、标题生成、概念注释、AI 请求和布局。应以职责拆出保存协调、AI 请求、概念标注等逻辑，并针对上述失败场景补回归验证；收益来自降低交叉状态错误，而不只是缩短文件。
- **先测真实规模，再优化列表。** 目前一次读取包含归档在内的所有卡片和正文，前端逐次进行字符串搜索，并渲染全部命中项。建议以 1,000 / 10,000 张包含长正文的卡片测量启动和搜索延迟，再引入分页、按需加载详情和虚拟列表。当前没有大规模基准数据，不能据此断言应用已经卡顿。
- **构建体积是跟踪项。** 当前主要 JS 文件约 854.89KB，构建产生超过 500KB 的提示；可按需加载编辑器、设置等模块。该提示不是已确认的启动性能故障，不应排在资料可靠性与阅读体验前面。
- **统一阶段说明。** AGENTS.md 项目定位仍描述第一阶段原型和多卡分析，PRODUCT.md 已明确转向真实桌面捕获与单卡 AI。后续应统一入口文档，减少未来实现重新偏向旧目标的可能。

## 设计评估

没有明显模板化渐变、装饰卡片或样式混用问题。优点是品牌色稳定、资料与个人判断分开、概念可返回原文。主要负荷来自多个编辑区域争夺阅读空间，而非单个菜单选项过多。

以下是界面评审的启发式评分，不是用户实验结果或完整可访问性认证；可靠性失败路径另按前文处理。

| 维度 | 分数 / 4 | 主要依据 |
|---|---:|---|
| 状态可见 | 3 | 保存状态明确，联网禁用原因不足 |
| 语言贴近用户 | 3 | 中文任务术语清楚 |
| 控制与自由 | 3 | 可停止、恢复，但流式滚动抢位 |
| 一致性 | 3 | 控件体系稳定，列表语义不一致 |
| 错误预防 | 3 | 删除确认、默认取消焦点 |
| 识别而非记忆 | 2 | 概念解释与快捷键发现性不足 |
| 效率 | 2 | 缺少状态队列与高效列表导航 |
| 简洁与美观 | 3 | 视觉克制，详情重复字段占空间 |
| 错误恢复 | 3 | 有恢复文案，部分回答保留不足 |
| 帮助说明 | 2 | 概念空态清楚，AI 首问引导不足 |
| 合计 | 27 / 40 | 优先提高阅读与整理效率 |

高频整理者需要待整理队列；新用户需要发现选中概念解释和 AI 首问；键盘与读屏用户需要明确的选中语义。捕获完成后的正向体验，应延续到“读清楚、形成判断、完成整理”。

## 验证结果与边界

- 独立静态 UI 扫描仅命中 1 条布局动画警告：`global.css:898` 对 padding-right 做过渡。属于 P3 排查项，未测得实际卡顿；已有减少动态效果支持，不应误报为缺失。
- 独立 Chrome 标签检查了纯前端空态和快速记录的键盘行为。浏览器缺少可用注入接口，未生成检查 overlay；纯前端没有 Tauri 服务导致的错误不计为原生应用故障。检查后已关闭自建标签和仅为评审启动的前端服务。
- 前端：31 个测试文件，199 项通过。
- Rust：231 项通过。
- Swift 原生：44 项通过。
- ESLint 和前端生产构建通过；构建有大文件提示。
- 未执行真实模型请求、真实卡片破坏性故障测试、全量键盘/VoiceOver 验收或大规模性能压测。
- 本轮不修改产品实现。评审归档放在项目已约定的 docs/，不创建新的评审目录。

## 建议实施顺序

1. 正文读取失败保护、AI 草稿上下文一致性、保留部分回答与滚动跟随。
2. 阅读空间、待整理筛选、删除弱化和 AI 空态说明。
3. 搜索找回、AI 内容回填、备份与导出；并随改动拆分对应复杂逻辑。

下一轮方案应先明确：默认打开卡片时以阅读为主、编辑为辅；收集箱以推进待整理队列为主。若日常实际使用重点相反，再调整布局和顺序。
