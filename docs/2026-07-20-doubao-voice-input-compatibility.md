# 豆包语音输入兼容性问题

## 1. 当前状态

- 状态：普通单行与多行纯文本字段已按可见 AppKit 控件路线实现，并通过代表字段实机验收。
- 发现日期：2026-07-20。
- 影响范围：IdeaCard macOS 桌面应用内的网页输入控件，包括普通输入框、多行文本框和结构化正文编辑器。
- 当前策略：不再使用隐藏输入桥或主动操作 WebView 输入上下文。需要豆包兼容的字段必须是真实、可见、直接承担输入的 AppKit 控件。

## 2. 问题表现

在 IdeaCard 桌面应用中，点击任一输入区域后按住 `Fn`：

- 豆包语音悬浮窗不出现。
- 语音识别结果不会进入当前输入区域。
- 普通键盘输入正常。

相同机器上的其他应用可以使用豆包语音输入。使用原生 macOS `NSTextField` 和 `NSTextView` 制作的测试应用也可以正常触发豆包语音输入。

## 3. 已完成排查

已确认以下因素不是问题原因：

- 麦克风权限或豆包自身设置。
- `Fn` 键不可用。
- IdeaCard 与测试应用的 Bundle ID 差异。
- 输入区域缺少 macOS 辅助功能文本角色。
- IdeaCard 注册的全局快捷键冲突。
- 仅由 TipTap 结构化编辑器引起，因为普通 HTML 输入框同样失败。

关闭 IdeaCard 全局快捷键监听后再次测试，问题仍然存在。系统输入法日志显示：IdeaCard 的 Tauri/WKWebView 输入区域获得焦点时，豆包没有向其发送最终文字插入事件；切换到原生输入控件后可以正常插入。

## 4. 当前判断

当前证据指向豆包输入法与 Tauri 在 macOS 上使用的 WKWebView 文本输入客户端之间存在兼容性问题。

该问题不能通过调整网页输入框属性、焦点逻辑或快捷键配置可靠解决。除非豆包或系统 WebView 后续修复兼容性，否则需要增加原生输入桥或调整桌面应用技术架构。

## 5. 已否决方案

### 5.1 `Fn` 后切换隐藏原生客户端

豆包会在 IdeaCard 切换前锁定输入目标，悬浮框和识别文字均不出现。

### 5.2 长期预备隐藏原生客户端

该方案可以获得豆包流式文字、正确光标和同屏悬浮框，但必须在每个物理按键前后切换 WebView 与 `NSTextView` 第一响应者，导致语音和普通键盘转圈、延迟，且曾破坏中文输入法。基础输入体验不合格。

### 5.3 主动激活 `WKContentView` 输入上下文

普通英文键盘恢复，但 macOS 输入源无法切换到中文；该方案同样停止。

上述失败方案的事件监听和输入上下文操作当前均已停用。

## 6. 已验证方案

### 真实、可见的原生标题字段

卡片详情“标题”保留 HTML input 作为布局、边框和非 Tauri 回退，在同一位置覆盖真实 `NSTextField`。用户实际点击、键盘输入、输入法组合、粘贴和豆包输入都由该原生字段直接处理；原生文本变化同步回 React 标题状态，原保存逻辑不变。

2026-07-27 实机确认以下四项全部正常：

- 普通键盘连续输入无延迟；
- 中文输入法可以正常切换和输入；
- 第一次按住 `Fn` 即可使用豆包，识别文字流式进入标题；
- `Command + V` 粘贴正常。

原生字段没有安装全局键盘/`Fn` 监听器，也不操作 WebView 输入上下文。前端 156 项测试、Rust 202 项测试、lint 和生产构建通过。

## 7. 当前边界与下一步

- 目前只有卡片详情标题使用真实原生字段。
- 普通网页 input、textarea 和 TipTap 仍保持原实现，豆包仍不可用。
- 单行普通字段已沿用可见 `NSTextField` 模式扩展，并由原生层按字段 ID 同时管理。
- 多行纯文本已接入可见 `NSTextView`，仍需单独完成键盘、中文输入法、豆包首次流式输入、当前光标和粘贴实测。
- 当前覆盖收件箱搜索、快速记录、确认捕获、概念名称以及卡片标题/想法/来源字段。
- TipTap、AI 对话输入框和设置页敏感字段不在本阶段范围内。

2026-07-27 扩展验收：收集箱搜索框与卡片“我的想法”均确认无问题，覆盖了单行和多行两种原生宿主。普通输入、豆包首次流式输入、当前光标和粘贴行为符合预期。
- TipTap 涉及富文本、图片、概念标记、选区和粘贴，不能直接降级为纯文本控件；需要独立的原生富文本承载或更窄的输入层方案。
- 后续扩展仍不得增加语音按钮、输入监控权限或隐藏第一响应者桥。
