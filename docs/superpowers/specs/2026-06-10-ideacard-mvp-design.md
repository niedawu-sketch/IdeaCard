# IdeaCard 第一阶段可交互原型设计

## 1. 文档目的

本文档定义 IdeaCard 第一阶段可交互前端原型的产品范围、核心对象、页面结构、关键流程、AI 延伸行为、技术结构和验收标准。

第一阶段用于验证产品体验，不实现真实 Mac 系统能力。验证通过后，再选择 Tauri、Electron 或 Swift 实现桌面应用。

## 2. 产品定位

IdeaCard 是一个面向 Mac 桌面端的想法、内容剪藏与分析工具。它解决的核心问题不是“保存更多信息”，而是降低从捕获信息到形成个人判断和结论的成本。

第一阶段采用“统一 Inbox”作为产品主线：

1. 用户通过快捷记录、剪贴板或截图 OCR 捕获内容。
2. 所有内容默认进入 Inbox，不要求用户立即分类。
3. 用户稍后补充自己的想法和处理状态。
4. 用户选择多张相关卡片组成分析集。
5. AI 根据用户输入的问题，对想法进行延伸、补充和不清楚信息的模拟查询，并保留来源引用。

## 3. 目标用户与场景

目标用户是需要高频阅读、记录问题并形成判断的知识工作者，例如产品经理、研究人员和内容创作者。

核心场景：

- 阅读公众号、网页、PDF 或其他内容时，快速保存重要片段并补充个人想法。
- 临时出现问题、判断或灵感时，通过全局快捷入口快速记录。
- 围绕一个议题选择多张卡片，让 AI 延伸想法、补充可能方向，并指出需要查询或确认的信息。

## 4. 第一阶段目标

- 验证统一 Inbox 能否同时承载文章剪藏、截图 OCR 和临时想法。
- 验证“捕获、处理、AI 延伸、形成结论”的完整闭环是否顺畅。
- 验证多卡片上下文是否能帮助 AI 更自然地延伸想法和暴露不清楚的问题。
- 验证 AI 结果引用具体卡片是否能增强结果的可信度和可追溯性。
- 验证菜单栏和全局快捷键能力在前端原型中的交互表达是否清晰。

## 5. 核心设计原则

### 5.1 捕获时不强迫整理

新内容自动进入 Inbox。捕获阶段只要求记录必要内容，不要求选择文件夹、项目或复杂分类。

### 5.2 个人想法与原始内容分离

卡片同时保留原始内容和“我的想法”。两者在界面和数据结构中明确区分，避免引用内容与用户观点混在一起。

### 5.3 AI 只处理用户明确选择的上下文

AI 不默认读取整个资料库。用户通过分析集决定本次包含哪些卡片，并填写想延伸或查询的问题。

### 5.4 结论必须可追溯

AI 生成的重要观点应引用对应卡片。用户可以从结论返回原始材料，判断结论是否合理。

### 5.5 第一阶段只验证关键假设

不引入文件夹层级、双向链接、知识图谱、云同步等功能，避免把原型做成通用知识管理系统。

## 6. 核心对象

### 6.1 卡片 Card

卡片是最小记录单元，可表示：

- 临时想法
- 文章摘录
- 剪贴板内容
- 截图 OCR 内容

卡片包含：

- 标题
- 原始内容
- 我的想法
- 类型
- 来源名称和来源地址
- 来源类型：个人记录、网页文章、文档资料、图片材料、音视频
- 处理状态
- 创建时间和更新时间

卡片状态：

- 未处理
- 已标注
- 待分析
- 已形成结论
- 已归档

### 6.2 收集箱 Inbox

Inbox 是所有新内容的默认入口，也是第一版主工作台。用户在这里完成搜索、按来源筛选、补充想法、修改状态、批量选择和归档。

### 6.3 分析集 Analysis Set

分析集是一次 AI 分析使用的材料包，包含：

- 分析集标题
- 想延伸或查询的问题
- 用户选择的卡片
- 生成状态
- 追问记录

分析集允许跨来源和时间选择卡片。用户可以在分析前添加或移除材料。

### 6.4 结论 Insight

结论是保存后的分析结果，包含：

- 直接回应
- 可延伸方向
- 需要查询或确认的信息
- 下一步行动建议
- 待验证问题
- 卡片引用
- 原始问题
- 追问记录
- 创建时间

结论与参与分析的卡片保持双向可访问关系，但第一阶段不实现通用双向链接系统。

## 7. 信息架构

第一阶段包含三个主要页面：

### 7.1 Inbox 工作台

采用桌面端三栏结构：

- 左栏：来源筛选。
- 中栏：搜索、捕获入口、卡片列表、批量选择。
- 右栏：当前卡片的原始内容、来源信息、我的想法、状态和操作。

### 7.2 AI 延伸工作台

采用双栏结构：

- 左栏：本次上下文包含的材料卡片，可添加、移除和查看。
- 右栏：想延伸或查询的问题、生成状态、AI 延伸结果、追问和保存结论操作。

### 7.3 结论页

展示已保存的结构化结论、追问记录和来源卡片。用户可以返回来源卡片，也可以基于原分析集继续分析。

## 8. 关键流程

### 8.1 快速捕获

1. 用户触发快捷记录、剪贴板或截图入口。
2. 原型展示对应的模拟捕获窗口。
3. 用户确认内容，必要时补充标题或想法。
4. 系统创建卡片并自动放入 Inbox。
5. 用户可立即关闭窗口，不要求继续整理。

目标：用户应能在 5 秒内完成一次纯文本快速记录。

### 8.2 Inbox 处理

1. 用户打开未处理卡片。
2. 查看原始内容和来源。
3. 在“我的想法”中补充判断、疑问或联想。
4. 标记为待分析。
5. 已处理但暂时无用的卡片可以归档。

### 8.3 创建 AI 上下文

1. 用户在 Inbox 或筛选结果中选择多张卡片。
2. 底部批量操作栏显示已选数量。
3. 用户点击“创建分析集”。
4. 系统进入 AI 延伸工作台，并带入已选卡片。
5. 用户填写想延伸或查询的问题。

### 8.4 AI 延伸与追问

1. 用户发起 AI 延伸。
2. 系统展示可取消的模拟生成状态。
3. 结果按固定结构展示，包含延伸方向、可执行下一步和需要进一步查询的信息，并引用相关卡片。
4. 用户可以针对当前分析集继续追问。
5. 用户确认结果后保存为结论。
6. 相关卡片状态更新为“已形成结论”。

## 9. AI 延伸设计

第一阶段的 AI 能力不是对材料或笔记做深度研究报告，而是帮助用户把已有想法往前推一步：延伸可能方向、指出不清楚的地方，并模拟及时查询后的补充信息。

AI 入口不提供模式分类。用户只需要填写一个问题，例如“这个想法还能往哪几个方向展开？”或“这里有哪些概念我需要查清楚？”。

默认输出结构：

1. 直接回应
2. 可延伸方向及对应卡片证据
3. 需要查询或确认的信息
4. 下一步行动建议
5. 尚未解决的问题

追问行为：

- 追问只基于当前分析集和已有生成记录。
- 用户可以引用某张卡片发起追问。
- 原型使用预置回答模拟追问过程。
- 保存结论时保留重要追问记录。

单卡片分析作为兼容能力保留：用户选择一张卡片时仍可创建分析集，但界面主路径优先引导多卡片分析。

## 10. 原型交互范围

原型需要实现：

- 快速记录、剪贴板和截图 OCR 的模拟捕获流程
- 卡片新增、编辑、搜索、筛选、多选、状态修改和归档
- 分析集创建、材料增删和延伸问题填写
- AI 模拟生成、取消、失败、重试和预置结果
- 结果中的卡片引用与定位
- 基于当前分析集的模拟追问
- 结论保存、查看和回链
- 浏览器本地数据持久化

原型异常状态：

- Inbox 无卡片
- 搜索或筛选无结果
- 捕获到重复内容
- OCR 识别失败
- 参考材料过多
- AI 延伸失败
- AI 延伸中途取消

原型判定规则：

- 新内容与已有卡片的来源地址相同，或去除首尾空白后的原始内容完全相同，则提示重复；用户仍可选择继续保存。
- 单个分析集最多包含 20 张卡片。超过后阻止发起 AI 延伸，并提示用户缩小材料范围。
- OCR 失败和 AI 延伸失败通过原型中的演示入口主动触发，不使用随机失败，保证测试过程可重复。
- 取消 AI 延伸后保留当前分析集和原始问题，不生成部分结论，用户可以重新发起延伸。

## 11. 技术结构

技术栈：

- React
- TypeScript
- Vite
- React Router
- Zustand
- localStorage

代码结构：

```text
prototype/
├── src/
│   ├── app/                 # 应用入口、路由、全局布局
│   ├── entities/
│   │   ├── card/            # 卡片模型与基础展示
│   │   ├── analysis/        # 分析集模型
│   │   └── insight/         # 结论模型
│   ├── features/
│   │   ├── capture/         # 三种模拟捕获入口
│   │   ├── inbox/           # 搜索、筛选、详情和批量操作
│   │   └── analysis/        # 分析生成、引用、追问和保存
│   ├── pages/               # Inbox、分析工作台、结论页
│   ├── shared/
│   │   ├── ui/              # 基础 UI 组件
│   │   ├── lib/             # 通用逻辑
│   │   └── styles/          # 设计变量和全局样式
│   └── store/               # Zustand 状态和本地持久化
└── tests/                   # 核心流程测试
```

设计约束：

- 不引入大型 UI 框架，建立满足原型需要的轻量组件规范。
- 原型按 Mac 桌面窗口设计，最低验证宽度为 1280 像素。
- 数据模型不依赖浏览器专属字段，为后续桌面端实现保留迁移空间。
- 模拟系统能力通过独立适配层提供，避免业务组件直接依赖假数据。

## 12. 验收标准

1. 用户能在 5 秒内完成一次纯文本快速记录。
2. 新内容无需选择文件夹或项目，自动进入 Inbox。
3. 用户能为卡片补充自己的想法并标记待分析。
4. 用户能跨来源选择多张卡片并创建分析集。
5. 用户能填写想延伸或查询的问题，不需要选择分析模式。
6. AI 模拟结果明确引用具体卡片，并能定位到对应材料。
7. 用户能基于当前分析集继续追问，并保存结构化结论。
8. 页面刷新后，卡片、分析集和结论仍然存在。
9. 无卡片、重复内容、OCR 失败、材料过多、分析失败和取消操作均可体验。
10. 在 1280 像素及以上宽度下，主流程页面无内容遮挡或不可操作区域。

## 13. 第一阶段不做

- 原生 Mac 菜单栏应用
- 真实全局快捷键
- 真实剪贴板监听
- 真实截图和 OCR
- 浏览器插件
- 真实大模型 API 和模型配置
- 账号、云同步和多人协作
- 文件夹层级
- 双向链接和知识图谱
- 移动端和 Windows 适配
- 数据导入导出

## 14. 后续实现方向

完成原型验证后，根据以下结果决定桌面端方案：

- 如果菜单栏、全局快捷键和系统截图体验是主要壁垒，优先评估 Swift。
- 如果希望复用前端原型并较快交付跨平台能力，优先评估 Tauri。
- 只有在依赖成熟 Node.js 桌面生态且包体积不是主要约束时，再评估 Electron。

后续阶段再决定真实 OCR 服务、大模型接入方式、本地数据库和同步方案，不在第一阶段提前绑定。
