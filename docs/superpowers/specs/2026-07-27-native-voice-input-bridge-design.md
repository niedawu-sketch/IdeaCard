# IdeaCard 原生语音输入桥设计规格

**日期：** 2026-07-27  
**状态：** 普通单行与多行纯文本字段已实现并通过实机验收  
**范围：** macOS 桌面端；不改变卡片、附件和数据库结构

## 1. 要解决的问题

IdeaCard 的所有可编辑区域由 Tauri 的 WKWebView 承载。普通键盘和系统输入法可以输入，但豆包语音输入在这些 WebView 文本客户端上无法通过按住 `Fn` 启动，也不会提交识别文字。相同机器上的原生 `NSTextField`、`NSTextView` 可以正常使用豆包语音输入。

本方案的验收目标不是增加一个“语音输入”按钮，而是：

> 光标位于 IdeaCard 任意受支持的可编辑区域时，用户直接按住 `Fn` 说话；说话过程中识别文字流式出现在原输入位置，松开后完成最终结果。

## 2. 约束

- 不迁移现有 React、TipTap、Tauri 架构。
- 不内置另一套语音识别，也不获取麦克风音频。
- 不读取、记录或持久化语音内容；原生层只暂存本次系统文本输入结果。
- 不通过剪贴板中转，避免覆盖用户剪贴板。
- 不要求用户额外点击语音按钮。
- 不增加语音按钮、浮层、状态条、提示面板或输入框状态；用户只使用豆包自身的语音交互。
- 不拦截后台应用中的 `Fn`；仅当 IdeaCard 为当前应用且存在有效编辑目标时工作。
- 不支持只读字段、禁用字段和密码/API Key 字段。
- 不把快速点击 `Fn`、`Fn + F1…F12`、`Fn + 方向键`误判为语音输入。

## 3. 核心判断

### 3.1 不继续修改网页输入框属性

普通 `input`、`textarea` 和 TipTap 都失败，且普通键盘输入正常，说明问题不在 React 的 `onChange`、输入框焦点样式或快捷键监听。继续增加 `keydown`、`beforeinput` 或 ARIA 属性不能让豆包把 WKWebView 识别为可用的原生文本客户端。

### 3.2 原生桥必须在主进程内

现有 Swift sidecar 是“一次请求、一次退出”的原生能力进程，适合 OCR 和截图，不适合本功能：

- sidecar 只能通过全局事件监听发现 `Fn`，会引入辅助功能权限和进程间时序；
- sidecar 激活自己的窗口会切换应用进程，增加豆包选错文本目标的概率；
- 常驻 sidecar 还需要新增生命周期与双向 IPC。

输入桥改为直接运行在 IdeaCard 主进程的 AppKit 层。Tauri 主窗口仍由 WebView 渲染，只有语音会话期间临时创建原生 `NSTextView`。

Apple 的 `NSEvent` 本地监听可以在事件分发到当前应用前观察 `flagsChanged`；`NSTextView` 是 AppKit 原生文本输入客户端，并应由所属窗口设为第一响应者：

- [NSEvent：本地与全局事件监听](https://developer.apple.com/documentation/AppKit/NSEvent)
- [NSTextView：文本输入与第一响应者](https://developer.apple.com/documentation/AppKit/NSTextView)

### 3.3 不适配豆包，适配 macOS 标准文本输入

第一次实机实现是在收到 `Fn` 后才把不可见 `NSTextView` 设为第一响应者。诊断记录证明目标注册、`Fn` 本地监听和第一响应者切换都成功，但豆包没有出现，也没有向原生控件写入文字。桌面原生验证 App 的关键差异是：按下 `Fn` 之前，当前第一响应者就已经是 `NSTextField` / `NSTextView`。

第二次实现让不可见 `NSTextView` 长期预占第一响应者，并在每次物理按键到达时切回 WebView。它虽然实现了首次语音、流式结果、正确光标和悬浮框屏幕，但实机会在语音和普通键盘输入时反复触发 macOS 输入法上下文重建，出现转圈和数秒延迟。该模型破坏了“普通键盘输入不变”的硬约束，判定为不可发布，不再继续叠加补丁。

第三次实现尝试保留 WebView 第一响应者，只主动调用 `WKContentView` 已有的 `NSTextInputContext.activate()`。实测普通英文键盘恢复，但 macOS 输入源无法切换到中文，说明主动激活 WebView 输入上下文同样改变了系统输入法状态。该方案也判定为不可发布。

当前实现回退到输入安全基线：

- WebView 始终保留第一响应者，不再创建或预备隐藏 `NSTextView`；
- 不主动激活、停用或替换 `WKContentView` 的文本输入上下文；
- 不监听或拦截 `Fn`、普通按键和输入法组合事件；
- 普通键盘、快捷键、粘贴、撤销和系统输入法始终走原 WebView 路径；
- 该方案不增加辅助功能、输入监控权限，也不增加可见语音 UI。

豆包语音在该安全基线上暂不生效。隐藏第一响应者桥和主动激活 WebView 输入上下文都不能在不破坏基础输入的前提下发布；后续只能评估真正的原生编辑控件或修复 Tauri/WKWebView 上游兼容性。本节后续交互时序保留为已验证失败方案的记录，不作为当前发布实现。

### 3.4 真实原生字段实验

用户确认继续验证后，新增一个严格限界的实验：只把卡片详情的“标题”改为真实、可见、可点击的 AppKit `NSTextField`，不再使用隐藏客户端，也不在 WebView 与原生控件之间转发键盘事件。

- HTML input 继续负责页面布局、边框、只读背景、标签关联和非 Tauri 环境回退；
- `NSTextField` 覆盖 HTML 字段的内容区域，成为用户实际点击和输入的控件；
- 原生字段的每次文本变化直接更新 React 的标题状态，原保存逻辑不变；
- React 因切卡或外部状态变化时，把新值同步回原生字段；相同值不重复写入，避免破坏中文输入法组合和豆包流式草稿；
- DOM 滚动、窗口缩放、字段被弹层遮挡或卸载时，同步更新、隐藏或销毁原生视图；
- 不安装本地键盘/`Fn` 监听器，不操作 WebView 的输入上下文；
- 实验只验证普通键盘、中文输入法、豆包首次流式输入和复制粘贴。四项通过前不扩展到正文、备注或 TipTap。

**实机结果（2026-07-27）：** 四项全部通过。卡片标题的键盘与中文输入法无延迟，豆包第一次按住 `Fn` 即可流式输入，复制粘贴正常。该结果证明可见原生控件路线成立，但只对当前 `NSTextField` 范围有效，不能直接推导 TipTap 也可同样改造。

### 3.5 已确认的扩展边界

扩展沿用“网页控件负责布局，真实可见 AppKit 控件负责输入”的路线，不再实施本规格 4～7 节记录的隐藏第一响应者桥。原生层必须允许多个控件同时挂载，字段之间切换时不能销毁其他可见控件，也不能操作 WebView 的第一响应者或输入上下文。

本阶段覆盖：

- 普通单行：收件箱搜索、快速记录标题、确认捕获标题、概念名称、卡片标题、来源名称、来源地址；
- 普通多行纯文本：快速记录“我的想法”、确认捕获正文与“我的想法”、卡片“我的想法”、AI 延伸提问；
- 单行使用可见 `NSTextField`，多行使用可见 `NSTextView`；
- 字段文本变化仍进入原有 React 状态、保存和校验流程；
- AI 延伸提问额外启用原生提交协议：未带 Shift 的换行命令发送当前问题，`Shift + Enter` 保留换行，输入法组合提交不得被误判为发送；
- 非 Tauri 环境和自动化测试继续使用原 HTML `input` / `textarea`。

本阶段明确排除：

- TipTap 富文本正文：包含图片、标记、选区与撤销历史，不能降级成纯文本；
- API Key、密码和模型设置字段：不扩大敏感信息经过原生桥的范围；
- `select`、checkbox、按钮和只读展示内容。

每一种新控件都必须重新通过普通键盘、中文输入法、首次豆包流式输入、光标位置和复制粘贴验收。单行字段已通过不能替代 `NSTextView` 的真实验收。

**扩展实机结果（2026-07-27）：** 用户分别在收集箱搜索框和卡片“我的想法”完成验收，确认单行 `NSTextField` 与多行 `NSTextView` 的普通输入、豆包首次流式输入、当前光标位置和粘贴均无问题。共用这两个宿主组件的本阶段普通文本字段可以按已实现范围保留。

**AI 延伸扩展（2026-07-31）：** AI 提问区复用已验收的可见 `NSTextView`，同时增加字段级 `submitOnEnter` 配置和 `native-text-area://submitted` 事件。原生层只接管未带 Shift 的换行命令，React 仍负责提交校验、发送状态、自动增高、错误恢复和发送后清空；不增加豆包专用 UI。

## 4. 交互时序

### 4.1 编辑目标注册

前端维护一个全局 `VoiceInputTargetRegistry`：

1. 普通 `input` / `textarea` 获得焦点时，记录元素、目标令牌、`selectionStart`、`selectionEnd` 和是否正在输入法组合。
2. TipTap 获得焦点或选区变化时，记录编辑器实例、目标令牌和 ProseMirror 的 `from` / `to`。
3. 每次焦点或选区变化，只向 Rust 上报目标令牌和“当前是否可接收语音”，不发送字段内容。
4. 目标卸载、变为只读、窗口切走或进入输入法组合状态时，暂停该目标。

目标令牌只在当前挂载周期有效。语音返回时必须仍匹配同一个令牌。

### 4.2 编辑目标聚焦与原生客户端预备

当前端注册有效目标时：

1. 前端等当前聚焦事件及浏览器默认行为完成，避免在 WebView 尚未建立文本输入上下文时抢走第一响应者；
2. 主进程在主窗口中创建或复用一个不绘制的原生 `NSTextView`；
3. 保存已经完成初始化的 WebView 第一响应者；
4. 在用户按 `Fn` 前通过 `makeFirstResponder` 激活原生文本客户端；
5. 同一目标在 `pointerup`、`keyUp` 或选区更新后再次上报时，先短暂恢复 WebView，再以最新光标和窗口位置重新预备原生客户端；
6. 目标切换时清空临时文本并更新目标令牌；
7. 目标失效时恢复 WebView 并释放原生客户端。

网页仍负责显示光标、选区和全部业务内容；原生客户端只接收一次语音会话的纯文本草稿。

### 4.3 `Fn` 按下

AppKit 层监听当前应用的：

- `flagsChanged`：识别物理 `Fn` / Globe 修饰键状态；
- `keyDown`：识别 `Fn` 组合的功能键或方向键；
- `keyUp`：补充取消组合键会话。

当有效编辑目标存在且检测到单独 `Fn` 按下：

1. 本地事件监听器只记录 `Fn` 是否按住和按下时间；
2. 不清空文本客户端、不切换第一响应者、不创建业务会话，也不向网页发送事件；
3. 豆包第一次真正写入原生文本后，输入桥才保存目标令牌并向前端发送 `voice-input://started`；
4. 如果第一份文字在 `Fn` 松开后才到达，会话在发送第一份草稿后立即进入已释放状态，继续接收豆包的最终修订。

豆包开始判断目标时，看到的已经是标准 macOS 文本输入客户端。原生文本视图不绘制、不参与布局、不接收鼠标，不产生任何 IdeaCard 自有界面。

把 `setString`、第一响应者切换或跨进程事件发送放在 `Fn` 本地事件监听器内，会与输入法管理器建立语音会话的过程发生重入，表现为应用短暂无响应和首次识别等待数秒。因此 `Fn` 路径只做常量时间的状态记录，业务会话由真实文本结果懒启动。

### 4.4 普通键盘、快捷键与鼠标

- 原生客户端处于预备状态时，任意物理 `keyDown`（语音使用的纯 `Fn` 修饰变化除外）先恢复 WebView 第一响应者，再把原事件继续交给网页；
- 网页收到对应 `keyUp` 后再次上报当前目标，待本轮事件默认行为完成后，主进程重新预备原生客户端；
- 鼠标点击和选区变化先由 WebView 正常处理，`pointerup` 的默认行为完成后再重新预备；
- 输入法组合文字期间目标暂停，组合结束后重新预备；
- 复制、粘贴、撤销、方向键和 Tab 均由原网页编辑器处理，不经过临时原生草稿。

### 4.5 快速点按与功能键

- `Fn` 在 180ms 内释放且原生文本没有变化：取消会话并恢复网页目标，不影响内容或界面。
- `Fn` 按住期间出现其他 `keyDown`：按功能键组合处理，立即取消语音会话，先恢复 WebView 第一响应者，再把原事件继续交给应用。
- 已经收到原生文本后，不再把会话回退为功能键组合。

这部分必须在真实 `.app` 中验证，不能只用单元测试推断。

### 4.6 流式草稿

豆包向临时 `NSTextView` 写入文字时，原生层监听文本变化，但监听回调内只登记一次待刷新任务。待本轮 AppKit 文本处理完成后，输入桥读取**当前完整草稿**，把同一轮的多次编辑合并为一次更新，再连同会话 ID 发送给前端。不能只发送新增字符，因为语音识别可能回改已经显示的词语、标点和分段。

前端把原选区视为本次会话的“临时范围”：

1. 第一份草稿替换原选区，或插入原光标位置；
2. 后续草稿始终整体替换上一份临时草稿；
3. 原输入框实时显示最新结果，不增加额外语音状态；
4. 临时草稿不进入正式撤销历史；
5. `Esc` 取消时删除临时草稿并恢复会话开始前的原文字和选区。

普通字段和 TipTap 都遵循同一个“原内容 + 临时草稿 + 最终提交”模型。前端不得根据前后字符串自行猜测增量。

### 4.7 松开与最终结果

豆包可能在 `Fn` 松开后才把最终文字提交给原生控件，因此松开不能立即结束会话：

1. `Fn` 松开后保持不可见原生文本客户端，等待豆包完成最后修订；
2. 继续监听 `NSTextView` 的文本变更；
3. 文本在 450ms 内不再变化后视为本次结果稳定；
4. 最长等待 8 秒；超时且无文字则结束，超时但已有文字则提交最后稳定内容。

前端负责稳定计时和最终提交，结束后调用原生命令释放临时原生第一响应者并恢复 WebView。最终提交时先无历史地恢复会话开始前的原内容，再用一次正式编辑操作写入最终文字，使整次语音输入只产生一个撤销步骤；这两个操作必须在同一事件循环内完成，不能造成可见闪烁。

### 4.8 回填与最终提交

提交时先校验：

- 目标令牌仍然存在；
- 目标仍可编辑；
- 目标内容没有被其他操作切换到不兼容状态；
- 当前不在输入法组合文本中。

然后：

- 普通 `input` / `textarea`：每份流式草稿替换当前临时范围并触发标准 `input` 事件；最终先恢复原值和原选区，再用一次正式编辑操作写入最终文字；
- TipTap：流式 transaction 使用 `addToHistory: false`；最终先用无历史 transaction 恢复原 slice，再用单个正式 transaction 插入最终纯文本；
- 多行结果保留换行；单行字段把换行规范化为空格；
- 流式期间原字段显示最新草稿但不抢回系统第一响应者；完成后光标位于最终文字末尾，并恢复到原网页编辑目标。

如果目标已卸载或令牌失效，不把文字插入其他字段；如果还能安全恢复原内容则回滚临时草稿并结束会话，不增加 IdeaCard 自有提示。

## 5. 无新增界面

输入桥只提供文本客户端兼容层：

- 不新增任何可见控件；
- 不显示“正在听写”“正在识别”等重复状态；
- 不复制豆包的音量、波形、草稿预览、确认或取消交互；
- 原字段只呈现豆包同步来的流式文字，与其他原生应用中的使用方式一致；
- 初始化或会话失败时保持普通输入可用，不弹出 IdeaCard 自有语音提示。

## 6. 模块边界

### 前端

- `desktop/src/features/voice-input/voiceInputTargets.ts`
  - 普通文本控件目标捕获与插入；
  - 目标令牌、选区和组合输入状态；
  - stale target 防护。
- `desktop/src/features/voice-input/VoiceInputBridge.tsx`
  - 监听 Tauri 原生事件；
  - 实时应用完整流式草稿；
  - 管理草稿稳定计时、超时、最终提交和取消回滚；
  - 在非 Tauri 测试环境安全降级。
- `RichTextEditor.tsx`
  - 注册 TipTap 目标；
  - 保存 ProseMirror 选区；
  - 用无历史临时 transaction 流式替换草稿，并用单个正式 transaction 提交最终文字。

### Rust / AppKit

- `desktop/src-tauri/src/native/voice_input.rs`
  - 安装 AppKit 本地事件监听；
  - 在目标聚焦后预备并管理挂在主窗口中的不可见 `NSTextView`；
  - 物理键盘事件到达前恢复 WebView 第一响应者；
  - 发送开始、释放和草稿事件；
  - 恢复主窗口与 WebView 第一响应者。
- `desktop/src-tauri/src/commands/voice_input_commands.rs`
  - 更新当前前端目标令牌；
  - 完成或取消当前会话；
  - 校验会话 ID，拒绝旧会话关闭新会话。
- `AppState`
  - 只保存可跨线程的目标和会话元数据；
  - AppKit 对象只存在于主线程，不进入 `AppState`。

`objc2`、`objc2-app-kit`、`objc2-foundation` 作为 macOS 直接依赖使用；它们已经是 Tauri 的传递依赖，本功能不引入新的运行时进程。

## 7. 状态模型

```text
idle
  └─ valid target focused → armed
armed
  ├─ physical key down → web_editing → key up / pointer up → armed
  └─ Fn down → capturing
capturing
  ├─ other key / quick Fn up → cancelling → idle
  ├─ Fn up → waiting_for_result
  └─ native text changed → streaming
streaming
  ├─ native text changed → replace provisional draft
  ├─ Fn up → waiting_for_result
waiting_for_result
  ├─ native text changed → replace provisional draft → waiting_for_stable_text
  ├─ no text timeout → cancelling → idle
waiting_for_stable_text
  ├─ text changes again → replace provisional draft → restart stable timer
  ├─ stable 450ms → committing → idle
  ├─ 8s timeout → committing last text → idle
```

任意状态收到不同会话 ID 的完成请求都必须忽略。

## 8. 失败与降级

- AppKit 初始化失败：保持网页输入正常，不拦截 `Fn`，记录稳定错误码，不崩溃。
- 没有有效目标：不启用原生文本客户端，不拦截 `Fn`。
- 未识别到文字：恢复原字段，不改变内容。
- 目标失效：回滚可安全恢复的临时草稿，不插入其他字段。
- 聚焦后预备的原生客户端仍不被豆包识别：停止后续实现，不静默改成“点击按钮再输入”。
- 不使用更早的 `CGEventTap`；该方案可能要求辅助功能或输入监控权限，不属于当前授权范围。

## 9. 验收标准

1. 标题、备注、多行内容、AI composer、概念助手 Prompt 和 TipTap 正文均可直接按住 `Fn` 输入，并在说话过程中看到流式文字。
2. 选中文字后语音结果替换选区；无选区时在光标处插入。
3. TipTap 插入保持图片和概念标记结构不损坏，一次 `Command + Z` 撤销整次语音输入。
4. 快速点按 `Fn` 不产生可见变化、不改变内容。
5. `Fn + F1…F12`、`Fn + 方向键`行为与未安装输入桥时一致。
6. `Esc` 取消后不插入任何临时或部分结果。
7. 切换卡片、关闭弹窗或目标卸载时，不把结果插入其他字段。
8. 只读归档内容、禁用字段和 API Key 字段不触发输入桥。
9. 拼音等系统输入法的组合文本不被打断。
10. IdeaCard 在后台时不监听、不激活窗口。
11. 不新增麦克风、辅助功能或输入监控权限要求。
12. IdeaCard 不新增任何语音按钮、浮层、面板、状态文字或错误提示。
13. 前端、Rust、Swift 现有测试与桌面构建全部通过。

## 10. 首个实现门槛

聚焦后预备方案先在普通文本框中做真实 `.app` 时序验证：

- 成功：目标聚焦后普通键盘仍正常；按住 `Fn` 时豆包悬浮窗出现，语音文字进入原生客户端并流式同步到原字段。然后回归快捷键、系统输入法和 TipTap。
- 失败：说明不可见标准原生客户端仍不能满足豆包的目标判断。直接 `Fn` 目标在当前权限边界内不可达，停止实现并报告证据。

这个门槛是技术可行性验证，不把未验证的焦点竞态扩散到完整代码。
